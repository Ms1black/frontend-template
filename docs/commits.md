# Conventional Commits

Все коммиты в проекте следуют спецификации [Conventional Commits](https://www.conventionalcommits.org). Это машиночитаемый формат, который позволяет автоматически генерировать changelog, определять тип изменений и упрощает навигацию по истории.

При каждом `git commit` сообщение автоматически проверяется через **Commitlint**. Если формат неправильный — коммит не пройдёт.

---

## Формат

```
<тип>(<область>): <описание>

[необязательное тело]

[необязательный footer]
```

### Обязательные части

- **тип** — категория изменения (см. таблицу ниже)
- **описание** — краткое пояснение в настоящем времени, строчными буквами, без точки в конце
- Максимальная длина заголовка: **72 символа**

### Опциональные части

- **область** в скобках — уточняет контекст изменения: `feat(auth)`, `fix(api)`
- **тело** — подробное описание через пустую строку после заголовка
- **footer** — ссылки на задачи, пометки о ломающих изменениях

---

## Типы коммитов

| Тип        | Когда использовать                                            | Пример                                       |
| ---------- | ------------------------------------------------------------- | -------------------------------------------- |
| `feat`     | Новая функциональность                                        | `feat(auth): добавить форму входа`           |
| `fix`      | Исправление бага                                              | `fix(api): обработать ошибку 401`            |
| `docs`     | Только документация                                           | `docs: обновить README`                      |
| `style`    | Форматирование и пробелы без изменения логики                 | `style: исправить отступы`                   |
| `refactor` | Рефакторинг без новой функциональности и без исправления бага | `refactor(user): упростить редьюсер профиля` |
| `perf`     | Улучшение производительности                                  | `perf(images): добавить lazy loading`        |
| `test`     | Добавление или исправление тестов                             | `test(button): покрыть обработку клика`      |
| `chore`    | Обновление зависимостей, конфигов, билд-скрипты               | `chore: обновить eslint до v10`              |
| `ci`       | Изменения в CI/CD                                             | `ci: добавить playwright в github actions`   |
| `revert`   | Откат предыдущего коммита                                     | `revert: feat(auth): добавить форму входа`   |

## Примеры

### Простой коммит

```
feat: добавить переключатель тёмной темы
```

### Коммит с областью

```
fix(auth): перенаправлять на логин при истечении токена
```

### Коммит с телом — когда нужно объяснить «почему»

```
refactor(api): заменить axios на нативный fetch

Axios добавляет ~14kb к бандлу, а используем мы только базовые GET/POST.
Нативный fetch с тонкой обёрткой покрывает все наши нужды.
```

### Ломающее изменение

```
feat(api)!: изменить формат ответа эндпоинта /users

BREAKING CHANGE: поле `data` теперь вложено в `result.data`
вместо того чтобы быть на верхнем уровне.
```

Восклицательный знак `!` после типа или области сигнализирует о ломающем изменении.

### Ссылка на задачу

```
fix(checkout): предотвратить двойную отправку при медленном соединении

Closes #142
```

## Частые ошибки

```bash
# ❌ Заглавная буква
feat: Добавить форму входа

# ❌ Точка в конце
feat: добавить форму входа.

# ❌ Прошедшее время
feat: добавил форму входа

# ❌ Слишком длинный заголовок (больше 72 символов)
feat(auth): добавить форму входа с валидацией email и индикатором надёжности пароля

# ❌ Неизвестный тип
update: что-то починить
```

```bash
# ✅ Правильно
feat(auth): добавить форму входа
fix: предотвратить сбой на пустом списке пользователей
docs(fsd): добавить пример структуры слайса
test(example): покрыть граничные случаи
chore: обновить playwright до 1.60
```

---

## Зачем это нужно

- **История читаема** — `git log --oneline` сразу показывает что менялось и где
- **Автоматический changelog** — инструменты вроде `semantic-release` генерируют его из коммитов
- **Семантическое версионирование** — `feat` → minor, `fix` → patch, `!` → major
- **Код-ревью** — ревьюер понимает намерение до просмотра диффа
